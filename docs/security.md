# Security

What the platform protects, how, and — just as importantly — what it does not
protect yet.

> **This project is alpha.** The controls below are real and implemented. They
> do not add up to a hardened production system, and this document will not
> pretend otherwise.

---

## Secret management

### Where secrets live

Infrastructure secrets live in `.env`, and nowhere else.

| Secret | Generated by | Stored in |
|---|---|---|
| `DJANGO_SECRET_KEY` | `openssl rand -base64 48` | `.env` |
| `POSTGRES_PASSWORD` | `openssl rand -base64 32` | `.env` |
| `INITIAL_ADMIN_PASSWORD` | `openssl rand -base64 24` | `.env` |
| `PLATFORM_ENCRYPTION_KEY` | `openssl rand -hex 32` | `.env` |

You are never asked to invent a credential, because credentials people invent
are credentials people reuse.

### How they are kept out of the repository and the image

- `.env` is in `.gitignore`, along with `*.pem`, `*.key`, `id_rsa*`, database
  dumps and coverage artefacts.
- `.env` is in `.dockerignore`. Without this, `COPY . .` bakes every secret into
  an image layer, where it survives deletion and travels with any registry push.
- `.env` is created with mode `600`.
- CI runs secret scanning and dependency review on every pull request.

### Rotating

```bash
# 1. Stop the stack
docker compose down

# 2. Edit .env

# 3. Restart
docker compose up -d
```

Rotating `DJANGO_SECRET_KEY` invalidates every session and every outstanding
password-reset token. Rotating `POSTGRES_PASSWORD` also requires changing it in
PostgreSQL itself.

## Network exposure

| Service | Published | Reachable from |
|---|---|---|
| `ansible-api` | `47420` | host |
| `ansible-postgres` | no | `ansible-network` only |
| `ansible-redis` | no | `ansible-network` only |
| `ansible-celery` | no | `ansible-network` only |
| `ansible-celery-beat` | no | `ansible-network` only |

Redis has **no authentication configured**. That is safe precisely because it is
unreachable from outside the Docker bridge — and it is why you must not publish
it. If you ever need to, configure `requirepass` first.

`docker-compose.dev.yml` publishes both to `127.0.0.1` for local development. It
binds to loopback, not `0.0.0.0`, and must never be applied to a deployed
environment.

## Container security

- Runs as an unprivileged user (uid 10001), not root.
- `HEALTHCHECK` declared, so orchestrators can detect a wedged container.
- Minimal base image (`python:3.12-slim`); only `curl` is added, for the
  healthcheck.
- `.dockerignore` keeps secrets, VCS metadata and test artefacts out of the
  build context.
- Gunicorn handles `SIGTERM` for a graceful stop.

Not done yet: read-only root filesystem, dropped capabilities, seccomp profile,
image signing, and a rootless daemon. All are appropriate next steps.

## Application security

### Transport and headers

| Control | Setting |
|---|---|
| Clickjacking | `X_FRAME_OPTIONS = DENY` |
| MIME sniffing | `SECURE_CONTENT_TYPE_NOSNIFF = True` |
| Referrer leakage | `SECURE_REFERRER_POLICY = same-origin` |
| HSTS | one year when `DEBUG` is off |
| Secure cookies | on whenever `DEBUG` is off |
| Session cookie | `HttpOnly`, `SameSite=Lax` |

### API

- Authentication is required by default; endpoints must opt out explicitly.
- Anonymous and authenticated requests are throttled.
- CORS denies every origin by default.
- CSRF protection is active on session-authenticated requests.

### Passwords

- Minimum 12 characters, with similarity, common-password and numeric-only
  checks.
- Hashed with Django's PBKDF2-SHA256 default; never stored or logged in clear.

### Audit

Every audit payload is redacted before it is written. See [audit.md](audit.md)
and [ADR 0010](adr/0010-audit-secret-redaction.md).

### Health endpoint

Deliberately returns booleans only. Failures are logged server-side with a
stack trace; the unauthenticated caller gets `{"database": false}` and nothing
that would help them.

## What is NOT implemented

Stated plainly, because a security document that only lists strengths is
marketing.

| Missing | Impact | Planned |
|---|---|---|
| **Per-scope RBAC** | Roles are implemented, but permissions are global — a role cannot yet be limited to one environment or asset group. | 0.3.0 |
| **MFA** | Password-only authentication. | Not scheduled |
| **Forced password change** | The generated admin password stays valid until someone changes it manually. | 0.2.0 |
| **Account lockout** | `SecurityEvent` can record failed logins; **nothing acts on them**. Brute-force protection is rate limiting only. | 0.2.0 |
| **Credential encryption** | `PLATFORM_ENCRYPTION_KEY` is generated but unused. There is no encrypted credential store yet. | 0.3.0 |
| **Audit log integrity** | The trail is append-only by convention and admin permission, not cryptographically. A database-level attacker can alter it. | Not scheduled |
| **Secrets manager integration** | No Vault, no KMS, no cloud secret store. | Not scheduled |
| **Security event alerting** | Events are recorded. Nobody is notified. | 0.5.0 |
| **TLS** | Not terminated by the platform. You must put a reverse proxy in front. | By design |

## Deploying more safely

If you are going to run this somewhere real despite the alpha status:

1. Terminate TLS at a reverse proxy; set `DJANGO_BEHIND_PROXY=True`.
2. `DJANGO_DEBUG=False`, and set `DJANGO_ALLOWED_HOSTS` to real hostnames.
3. Change the admin password immediately.
4. Put the whole stack on a private network; do not expose 47420 to the
   internet.
5. Back up PostgreSQL, and **test a restore** — an untested backup is a hope.
6. Ship logs somewhere they cannot be deleted by whoever compromises the host.
7. Keep images updated; Dependabot will open the pull requests.
